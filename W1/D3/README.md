# День 3 — диалог с reasoning и четыре способа решения

CLI сохраняет многоходовый диалог с настройками reasoning и поддерживает
проверку каталога, два пилотных запроса и основной эксперимент на восьми задачах.
Результаты пилота — в `submission/pilot-report.md`. Основное сравнение использует
минимальный и максимальный бюджеты thinking. Предыдущая проверка off сохранена
отдельно: провайдер сообщил ненулевой счётчик, поэтому режим не называется выключенным.
Основной прогон завершён: 64 результата, 80 вызовов, 5 разрывов соединения без повторов.
Итоговый отчёт и исходные данные для сдачи находятся в `submission/`.

## Установка и запуск

```bash
cd /Users/brestkin/ai-advent-challenge-10/W1/D3
python3 -m venv .venv
.venv/bin/python -m pip install --upgrade pip
.venv/bin/python -m pip install -e '.[test]'
.venv/bin/day3 --help
```

В текущей рабочей папке установка уже выполнена. Настройки загружаются в порядке:
`.env` D1 → `.env` D2 → `.env` D3 → переменные окружения. Более поздние настройки
имеют приоритет, включая пустые значения. Ключ повторно вводить не нужно, если
он настроен в D1. Для отдельной установки заполните локальный `.env` по примеру.

Модель: `google/gemini-2.5-flash-lite`. Маршрут: `google-ai-studio/flex`.
`--model` и `--provider` позволяют явно задать настройки, однако текущий профиль
максимального thinking-бюджета проверяет только эту модель. Для другой модели
нельзя переносить число 24576 и называть его максимумом без отдельного профиля.

```bash
.venv/bin/day3 catalog
.venv/bin/day3 chat --session learning --reasoning max
```

`catalog` читает публичные сведения без платной генерации. `chat` тарифицирует
каждое отправленное сообщение вместе с историей. Команды `/history`, `/new`,
`/exit` сохранены. Запуск с существующим `--session` продолжает разговор,
без имени — создаёт новый. EOF завершает работу, Ctrl+C даёт код 130.

## Reasoning и история

Профили запросов:

| Режим | Объект reasoning | Смысл |
|---|---|---|
| off | `{"enabled": false}` | Запрос отключения thinking; фактический счётчик проверяется отдельно |
| min | `{"enabled": true, "max_tokens": 512}` | Минимальный thinking-бюджет этой модели; режим по умолчанию |
| max | `{"enabled": true, "max_tokens": 24576}` | Максимальный заявленный thinking-бюджет этой модели |

Общий `max_tokens` — 32768 в обоих режимах, temperature — 0.7.
Максимальный бюджет не заставляет модель расходовать его целиком.
Пошаговое объяснение в обычном тексте возможно и при запросе off.
Поле `reasoning_effort` верхнего уровня не используется: документация Polza.ai
предупреждает, что оно игнорируется; применяется вложенный объект reasoning.

История `history/<имя>.json` хранит модель, маршрут, режим, общий лимит,
temperature и успешные пары user/assistant. Режим восстанавливается при
продолжении. Явная попытка изменить настройки существующей сессии отклоняется;
для другого режима создайте новое имя разговора. `/new` сохраняет прежний файл
и начинает отдельный разговор с теми же настройками.

Повреждённая история не перезаписывается. При ошибке API, обрезании или отказе
незавершённый ход остаётся в журнале и не попадает в успешный стек. Сохранение
атомарное. Одновременное редактирование одного разговора несколькими процессами
не поддерживается; обнаруженная внешняя правка останавливает добавление хода.
Контекст автоматически не обрезается: если он переполнен, начните новый разговор.

Таймаут подключения — 10 секунд, чтения — 180 секунд. Они задаются через
`--connect-timeout` и `--read-timeout`. Таймаут чтения — ожидание данных,
а не общий дедлайн процесса. Общий лимит нового разговора меняется через
`--max-tokens`, допустимы значения 24577–65535. Это верхняя граница генерации,
а не заранее оплачиваемый объём: тарифицируются использованные токены.

## Проверка модели перед экспериментом

```bash
.venv/bin/day3 pilot
```

Команда делает **ровно два платных вызова**, по одному на min и max; автоматических
повторов нет. Используется одинаковая задача T8, прямой ответ и одна строгая схема.
До генерации проверяются конкретный маршрут, параметры, заявленные capabilities,
лимит и рублёвые цены. В запросе закреплён provider.only, отключён fallback,
включён require_parameters. Цена маршрута ограничивается снимком каталога с запасом 1%.

Пилот проверяет завершение, схему, модель, обязательные метрики и использование
режимов min/max: оба счётчика должны быть положительными, а на проверочной задаче
у max должен наблюдаться больший расход thinking, чем у min. Это консервативная
проверка наблюдаемого эффекта, а не обещание тратить больше токенов на каждом запросе. Если
метрика отсутствует, она остаётся неизвестной. Подтверждается также учёт
total=prompt+completion и reasoning_tokens≤completion_tokens: thinking не
прибавляется к total второй раз. Неверное решение самой задачи не является
само по себе признаком неподдерживаемого API-параметра.

Файлы: `pilots/<дата_id>/pilot.json`, `off.json`, `max.json`, `catalog.json`,
`report.md`. Повторный запуск создаёт новый набор и новые платные запросы.
Один пилот не доказывает точную внутреннюю реализацию бюджетов провайдером.

**Первый пилот off/max:** при enabled=false API сообщил 2 reasoning-токена,
при max — 3955. verified=false; запуск не разрешался. Причина малого ненулевого
счётчика не установлена, его нельзя менять на ноль или без подтверждения называть
служебным. **Согласованный второй пилот min/max:** 366 и 2126 thinking-токенов;
verified=true. Максимальный бюджет мягкий: фактическое число токенов может быть ниже.

## Основной эксперимент

```bash
.venv/bin/day3 experiment --pilot /абсолютный/путь/к/успешному/pilot.json --budget-rub 10
```

Команда требует успешный пилот с теми же моделью, маршрутом, схемой, режимами
и набором задач. Для текущего эксперимента согласован бюджет 10 ₽.
Повторный запуск без --resume создаёт новый набор и новые платные запросы.

Восемь задач × четыре метода × два режима = 64 решения и до 80 API-вызовов:

| Метод | Реализация |
|---|---|
| direct | Прямой ответ без объяснения |
| stepwise | Просьба решить пошагово с кратким объяснением |
| metaprompt | Первый вызов составляет промпт; второй использует его в том же разговоре |
| experts | Аналитик, инженер и критик в одном вызове; ответ каждого и общий итог |

Эксперты — роли одной модели, не независимые агенты. Финальная JSON Schema
одинакова. Для этапа составления промпта используется отдельная схема с полем prompt.
Эталоны не передаются в запросах. Каждое решение начинает чистую историю,
между этапами метапромпта сохраняется стек. При сбое первого этапа второй
не отправляется. Оба этапа используют одинаковый выбранный режим reasoning.

Проверяются формат, завершённость и соблюдение метода, затем ответ сравнивается
с эталоном. Дроби сравниваются точно как рациональные числа; множество рыцарей
допускает другой порядок, последовательность T7 — нет. Условия: `TASKS.md`;
проверяющий код и эталоны — `src/day3/tasks.py`.

В итог за метод входят все реально сделанные вызовы, входные/выходные/общие/
reasoning-токены, стоимость и сумма времени HTTP-операций. Отсутствующие метрики
не считаются нулями; суммы известных значений сопровождаются счётчиками unknown_*.
Ошибка API, неверный формат, обрезание, нарушение метода и неправильный ответ
учитываются отдельно. При прерывании метапромпта расходы первого этапа сохраняются.

Порядок 64 решений перемешан с seed=42. Одна попытка на комбинацию не измеряет
устойчивость: отсутствие разницы на восьми задачах не доказывает бесполезность приёма.

Сохраняются `results/<дата_id>/results.json`, `summary.csv` (8 строк),
`details.csv` (до 64 строк), `comparisons.csv` (попарные изменения относительно
прямого ответа), `interactions.csv` (изменение выигрыша при переходе min→max),
`report.md`, `raw/*.json`, снимок каталога и задачи.
В таблице отдельно показаны верный ответ и полный успех с соблюдением метода.
Из анализа качества исключаются пары с отсутствующим/невалидным ответом;
при сравнении выигрыша min и max используется общий для обоих режимов набор задач.
Сетевая ошибка не считается доказательством ухудшения промпта.
Частичные результаты помечаются interrupted или budget_stopped.

Продолжение без повторения выполненных попыток:

```bash
.venv/bin/day3 experiment --pilot /путь/к/pilot.json --budget-rub 10 --resume /путь/к/папке/прогона
```

Сохраняются прежний бюджет и настройки. Готовая попытка с ошибкой API также
не повторяется: это отдельный результат, а не повод незаметно добавить запрос.
Переход после каждого этапа метапромпта записывается в raw. Прерывание после
первого этапа сохраняет расход; неполный метод остаётся результатом с ошибкой.

### Ограничение расходов

Перед каждым вызовом резервируется консервативная оценка: общий лимит выхода
и размер входа в байтах с запасом на служебные поля. При неизвестной стоимости
вызова эта верхняя оценка остаётся зарезервированной: неизвестное списание
не считается нулём. При продолжении резерв восстанавливается из исходного запроса.
Дальнейшие запросы отправляются только при наличии бюджета с учётом резервов.
Это локальная защита с ценовым ограничением маршрута, а не банковская гарантия
биллинга. Цена и правила токенизации провайдера могут потребовать отдельной проверки.

## Логи, ключи и тесты

Каждый запуск создаёт `.log` с локальной датой и временем до секунд и уникальным
идентификатором. Записываются ввод, консольный вывод, запросы, ответы, метрики,
ошибки и пути файлов. Известный ключ заменяется на [REDACTED]; Authorization
не записывается. История и журналы создаются с правами 600. Если журнал создать
или записать нельзя, работа останавливается; если диск отказал после запроса,
физически сохранить запись может быть невозможно.

Личные `history/`, `logs/`, `pilots/`, `results/` и `.env` исключены из Git.
В `submission/` помещаются только проверенные учебные артефакты.
Файлы содержат тексты запросов и ответов — проверяйте их перед публикацией.

```bash
.venv/bin/python -m pytest -v
```

Тесты офлайн, не расходуют API-баланс. Цикл BDD описан в `BDD.md`.
Коды завершения: 0 — нормальное завершение; 1 — ошибка/непройденный пилот/
остановленный эксперимент; 2 — неверные настройки; 130 — Ctrl+C.
