# День 2 — диалог с историей и контроль формата ответа

Приложение умеет вести многоходовый диалог, продолжать сохранённые разговоры и
сравнивать шесть способов управления форматом одного запроса.

## Быстрый запуск

```bash
cd /Users/brestkin/ai-advent-challenge-10/W1/D2
python3 -m venv .venv
.venv/bin/python -m pip install --upgrade pip
.venv/bin/python -m pip install -e '.[test]'
.venv/bin/day2 chat --session python-learning
```

В текущей рабочей папке установка уже выполнена. Ключ не нужно вводить повторно:
настройки читаются из `W1/D1/.env`, затем поверх накладывается `W1/D2/.env`,
затем переменные окружения. Нужны `POLZA_API_KEY` и `LLM_MODEL`.
При отдельной установке скопируйте `.env.example` в `.env` и заполните ключ локально.
Пустое значение в `.env` D2 также перекрывает настройку D1.

Три режима:

```bash
.venv/bin/day2 chat --session python-learning
.venv/bin/day2 catalog
.venv/bin/day2 experiment --repeats 5
```

`catalog` обращается только к публичному списку моделей, без платной генерации.
`experiment --repeats 5` отправляет 30 платных запросов, без повторов.
Запуск без `--session` всегда начинает новый разговор; существующее имя продолжает его.
Имена разговоров: латинские буквы, цифры, дефис и подчёркивание.

## Диалог

```text
Вы> Меня зовут Анна. Запомни это.
Модель> ...
Вы> Как меня зовут?
Модель> ...
Вы> /history
Вы> /exit
```

Команды:

| Команда | Поведение |
|---|---|
| `/history` | Показать сообщения текущего разговора |
| `/new` | Начать отдельный разговор с пустой историей; предыдущий файл сохраняется |
| `/exit` | Завершить работу |

В `history/<имя>.json` хранятся версия формата, модель, параметры и чередующиеся
сообщения user/assistant. Каждый новый запрос содержит весь успешный стек ходов.
После ответа история автоматически сохраняется атомарной заменой файла.
При повторном запуске с тем же именем модель и параметры должны соответствовать
сохранённым; лимит сохранённого разговора восстанавливается автоматически.

Лимит нового разговора — 4096 токенов, temperature — 0.7.
Другой лимит можно задать при создании: `day2 chat --session short --max-tokens 1500`.
Таймаут подключения — 10 секунд, чтения — 60 секунд. Их можно изменить параметрами
`--connect-timeout` и `--read-timeout`. Таймаут чтения не является общим дедлайном процесса.

При сетевой ошибке, отказе, обрезании или невозможности сохранить ответ незавершённый
ход остаётся в журнале, а стек успешных ходов не меняется. Можно продолжить разговор.
Ctrl+C завершает работу с кодом 130, EOF — обычный выход.
Разговор рассчитан на один активный процесс; обнаруженная внешняя правка истории
останавливает добавление хода, но это не полноценная блокировка конкурентного доступа.
История не обрезается автоматически: если контекст станет слишком большим,
API вернёт ошибку; начните новый разговор через `/new`.

## Эксперимент

Во всех вариантах используется одна задача: «Составь три идеи заданий для изучения
Python: название, уровень сложности и длительность в минутах».

| Вариант | Изменение |
|---|---|
| baseline | Без требования JSON |
| prompt_json | Явное описание JSON и полей в системной инструкции |
| token_limit | Та же инструкция и max_tokens=32 |
| stop_sequence | Та же инструкция и stop на строке `"level"` |
| json_mode | Та же инструкция и response_format=json_object |
| strict_schema | Та же инструкция и response_format=json_schema, strict=true |

Строка стоп-последовательности в Python: `['"level"']`. Она выбрана намеренно
внутри ожидаемого JSON, чтобы проверить последствия остановки посередине структуры.
Лимит 32 токена также является стресс-проверкой, а не рекомендуемой настройкой.
Для остальных вариантов установлен max_tokens=4096. Temperature=0.7.

Каждый прогон использует новую историю с одним пользовательским сообщением.
Ответы предыдущих прогонов не попадают в следующие. Внутри каждого повтора порядок
шести вариантов перемешивается с seed=42, чтобы уменьшить влияние очередности.
Это независимые задачи в смысле контекста; статистическая независимость работы
backend и отсутствие кэша не гарантируются.

Перед генерацией приложение проверяет параметры модели по каталогу и сохраняет
его снимок. Поддержка в каталоге — предварительная проверка; ошибки фактического API
всё равно учитываются. Модель фиксирована, backend выбирается шлюзом.
Отключены HTTP-повторы, перенаправления и fallback; require_parameters=true.

Три независимые проверки ответа:

1. **Разбор JSON:** исходный текст должен разбираться без удаления Markdown и
   исправления обрезанных фрагментов. NaN и дублирующиеся ключи отклоняются.
2. **JSON Schema:** обязательные поля, типы, допустимые уровни и отсутствие лишних полей.
3. **Требования задания:** ровно три идеи, разные непустые названия, положительные длительности.

Схема специально проверяет структуру, а количество идей и положительность чисел
проверяются отдельно. Смысловая полезность идей автоматически не оценивается.
При неверной структуре требования к данным не оцениваются: task_evaluated=false,
а в подробной Markdown-таблице стоит «—». Это не оценка содержательной правильности свободного текста.
Полный успех — выполнение требований при полном ответе и отсутствии ошибки API.
`finish_reason=stop` само по себе не подтверждает корректность JSON.

В `results/<дата_время_id>/` сохраняются:

- `report.md` — сводная таблица, подробные результаты, примеры и выводы;
- `details.csv` — 30 строк с метриками каждого запроса;
- `summary.csv` — 6 строк со сводкой по вариантам;
- `results.json` — настройки, запросы, ответы, проверки и метрики;
- `raw/*.json` — отдельная запись каждого прогона;
- `catalog.json` — возможности и цены перед экспериментом.

CSV — UTF-8 с BOM для открытия в табличных редакторах. Пустая стоимость означает
неизвестное значение, а не бесплатный запрос. При пропусках итог содержит только
известные расходы, число пропусков вынесено отдельно. При прерывании уже завершённые
прогоны и частичный отчёт сохраняются со статусом interrupted. Продолжения того же
эксперимента нет: повторный запуск создаёт новый набор и новые платные запросы.

Пять повторов одного запроса не доказывают надёжность на всех задачах.
Фактические результаты готового прогона находятся в `submission/`.

## Журналы и локальные данные

Каждый запуск создаёт `logs/YYYY-MM-DD_HH-MM-SS_<id>.log` в UTF-8.
Записываются ввод и команды, отправленный стек сообщений, ответы API, метрики,
ошибки, пути сохранения и завершение. Все сообщения консоли также записываются.
Время в записях содержит смещение часового пояса.
Известный API-ключ заменяется на `[REDACTED]`, Authorization не записывается.
Файлы логов и JSON-истории создаются с правами 600.

История, журналы, сырые результаты запусков и `.env` исключены из Git.
Запросы и ответы могут содержать ваши данные: файлы из `submission/` предназначены
для сдачи и должны содержать только проверенные учебные примеры.
Если журнал недоступен, выполнение останавливается до отправки запроса.
Если диск перестал работать после отправки, сохранить журнал физически невозможно.

Коды завершения: 0 — обычное завершение команды; 1 — ошибка выполнения;
2 — неверные настройки/аргументы; 130 — Ctrl+C. В режиме диалога отдельная
ошибка запроса показывается, после чего можно продолжить. В режиме эксперимента
код 0 означает, что все попытки учтены, а не что все ответы корректны.
